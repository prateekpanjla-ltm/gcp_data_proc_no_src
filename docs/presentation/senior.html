Why Manage Permissions in Code?

Without Infrastructure as Code

  • Permissions granted manually via web console
  • No record of who granted what or when
  • "It works on my machine" — can't reproduce
  • Forgotten permissions accumulate over time
  • Audit = screenshot archaeology

With Infrastructure as Code (Terraform)

  • Every permission is a line of code in Git
  • Pull request = permission review before it's applied
  • Full history: who changed what, when, why
  • Destroy + rebuild proves no hidden manual steps
  • Audit = read the code
Imagine if every office key card assignment had to go through a pull request. That's what we're doing for cloud permissions.

Three Types of Identities in GCP

Every action in GCP is performed by an identity. We use three types:

Type 1 Deployer Account

"The construction crew"

  • Runs the automation (Terraform)
  • Builds and configures everything
  • Has broad permissions — but only for setup
  • Needs permission to assign other accounts to services

Type 2 Runtime Accounts

"The employees with specific job roles"

  • One per service (downloader, processor, loader)
  • Minimal permissions — only what the service needs
  • If compromised, blast radius is limited
  • Created by the deployer, used by the service

Type 3 Google Service Agents

"The building management system"

  • Google-managed, handles infrastructure plumbing
  • Routes events between services
  • Generates authentication tokens
  • Needs explicit permission grants (not automatic!)
Most tutorials use one account with full access (like giving every employee a master key). We use separate accounts with minimum permissions (like specific key cards per floor).

Lesson 1: The "Associate" Permission

When our automation creates a service, it needs permission to assign an identity to that service.

The confusing part

  • GCP calls this permission "actAs" (and sometimes "impersonation")
  • It's neither — it's really "associate this account with this service"
  • Google's own docs page is titled "Attach service accounts to resources"
  • The permission name (serviceAccountUser) sounds like "use the account" — but it means "assign it"

Why it catches people off guard

  • Creating an account needs one permission
  • Assigning that account to a service needs a different permission
  • Most people assume creating = ability to use. It's not.

We ran an experiment: removed the "associate" permission, enabled detailed logging, and compared.

  • We also found our deployer had an unnecessary permission (tokenCreator) that we safely removed
  • Takeaway: Enable audit logging to verify your security model — don't just trust documentation

Lesson 2: Authentication Between Services

When one service needs to call another, it needs a temporary credential (token). Someone has to create that token.

The scenario

  • A scheduler triggers a data processing job every hour
  • The processing job requires authentication (no anonymous access)
  • The scheduler can't generate credentials itself
  • It asks a Google-managed agent to create a temporary token
  • The agent needs explicit permission to do this

What happens if this is missing

  • The scheduler fires on time
  • The event reaches the target service
  • But authentication fails — silently
  • No error in the scheduler logs
  • You only find out when you check the target service
sequenceDiagram
  participant S as Scheduler
  participant A as Google Agent
  participant T as Target Service
  S->>A: I need to call Target Service
  A->>A: Do I have permission to create a token?
  A->>S: Here's a temporary token (valid ~1hr)
  S->>T: Request + token
  T->>T: Verify token
  T-->>S: Success
Think of it as a receptionist (Google agent) who can issue visitor badges (tokens). The receptionist needs authorization to issue badges for specific floors (services).

Lesson 3: Google's Agents Are Not Ready by Default

When you enable a Google service (like event routing), Google creates a service agent to manage it. But it's not created immediately.

The problem

  • You enable a service (e.g., "turn on event routing")
  • Google says "Done!" — but the agent isn't ready yet
  • Your automation tries to grant permissions to the agent
  • Fails because the agent doesn't exist yet
  • This is intermittent — sometimes it works, sometimes not

The fix

  • Explicitly activate each agent before granting permissions
  • We added a step that says: "Create the agent NOW, don't wait"
  • Then verify the agent exists before proceeding

Lesson 4: Permissions Take Time to Activate

GCP permissions are eventually consistent — the system confirms a permission is granted, but it may not be active for up to 7 minutes.

Common approach: Just wait

  • Add a 60-second delay after granting permissions
  • Wasteful if permission activates in 10 seconds
  • Unreliable if it takes 5 minutes
  • No way to know if it actually worked

Our approach: Verify, then proceed

  • After granting, we poll: "Can this account actually access the resource?"
  • Check every 10 seconds, up to 2 minutes
  • Proceed as soon as confirmed — no wasted time
  • If it fails after 2 minutes, we know something is wrong
flowchart TD
  G[Grant permission] --> V{Verify: can\naccount access\nresource?}
  V -->|"Not yet"| W[Wait 10 seconds]
  W --> V
  V -->|"Yes!"| P[Proceed with deploy]
  V -->|"2 min timeout"| E[Error: investigate]
  style P fill:#e6f4ea,stroke:#188038
  style E fill:#fce8e6,stroke:#c5221f
Like waiting for a new employee's badge to activate — you don't just hope it works. You test the badge at the door before sending them to their desk.

This caught a real bug: a build account had permissions granted but couldn't access its build storage for 45 seconds.

Lesson 5: The Silent Failure Chain

Our event-driven pipeline requires 5 separate permission grants. If any one is missing, events are lost — with no error visible to the operator.

flowchart LR
  GCS[File uploaded\nto storage] -->|"1. Storage agent\ncan publish events"| PS[Event bus]
  PS -->|"2. Event service\ncan receive events"| EA[Event router]
  EA -->|"3. Invoker account\ncan call the service"| CR[Processing\nService]
  EA -.->|"4. Invoker account\ncan receive events"| EA
  PS -.->|"5. Event bus agent\ncan create auth tokens\nfor invoker account"| CR
  style GCS fill:#e6f4ea,stroke:#188038
  style CR fill:#e8eaf0,stroke:#1a56db

What "silent failure" means

  • The file upload succeeds
  • The event fires correctly
  • The event reaches the target
  • But authentication fails (missing grant #5)
  • No error in the event logs — only in the target service logs

Our fix

  • All 5 grants are declared in code
  • The event trigger won't be created until all 5 are confirmed
  • If any grant fails, deployment stops with a clear error
  • No partial deployments that look working but aren't

Key Takeaways

1. Separate accounts for separate jobs

One master key for everything is a security risk. Each service gets its own account with minimum permissions. If one is compromised, the blast radius is limited.

2. "Associate" and "Token Creator" are hidden requirements

The deployer needs permission to assign accounts to services. Google agents need permission to create authentication tokens. Missing either causes silent failures.

3. Google's agents aren't ready immediately

Enabling a service doesn't mean its support infrastructure is ready. Explicit activation avoids intermittent failures.

4. Permissions are eventually consistent

Granting a permission doesn't mean it's active. Verify before proceeding — don't assume. This makes CI/CD pipelines reliable instead of flaky.

5. Infrastructure as Code proves itself on rebuild

The real test: destroy everything and rebuild from code. If it works, your automation is complete. If not, there are hidden manual steps.

Business impact

Auditable permissions. Reproducible environments. Fast disaster recovery. No tribal knowledge locked in someone's head.

Next Steps

Eliminate long-lived credentials

Currently: we download a key file for the deployer account. This key doesn't expire and audit logs don't show who used it.

Better: Workload Identity Federation — GitHub Actions authenticates directly with Google Cloud. No keys to manage, rotate, or accidentally leak. Audit logs show the exact person/workflow that triggered the action.

Remove over-provisioned permissions

Our audit log experiment found that the deployer has a permission (tokenCreator) it doesn't actually need. Removing unnecessary permissions reduces attack surface.

Reusable permission templates

Package the "create account + assign permissions + associate with service" pattern into reusable modules. New services get correct permissions by default.

Organization-level policies

Enforce rules like "no service account keys" and "no Editor role" at the organization level, so individual projects can't bypass security.

Automated permission auditing

Alert when permissions are granted outside of Terraform. Ensures all changes go through code review.
