GitHub Archive publishes hourly JSON.gz files with all public GitHub events (~150K/hour). Pipeline has 4 phases, event-driven via Eventarc. Each phase uses a different GCP product. 6 dedicated SAs (one per component). Also built on Dataproc and Data Fusion branches.

Why Terraform for IAM?

  • Every IAM binding is in version control -- auditable, reviewable, reproducible
  • Destroy and reprovision from scratch proves the IAM model is complete
  • No manual Console clicks that get forgotten or undocumented
  • Environment parameterization: same IAM model for dev/test/prod
  • The real test: terraform destroy && terraform apply -- does it still work?
  • That's where I found all the interesting IAM bugs
The real value of IaC for IAM: every binding is auditable and version-controlled. The destroy+reprovision test is the ultimate validation. If you can't tear it all down and rebuild, your IAM model has hidden manual steps.

The 3-Layer IAM Model

Layer 1 Terraform Deployer SA

  • "Who runs terraform apply?"
  • test-tf-deployer@project.iam
  • 26 project-level roles
  • Must "associate" (actAs) every runtime SA

Layer 2 Runtime SAs

  • "Who does the actual work?"
  • downloader -- storage, logging
  • processor -- storage, monitoring
  • bq-loader -- bigquery, storage

Layer 3 Service Agents

  • "Who does Google's infra work?"
  • Scheduler agent -- tokenCreator
  • Storage agent -- pubsub.publisher
  • Pub/Sub agent -- tokenCreator

Key insight: Most tutorials show one SA with Editor role. Production needs this 3-layer model.

The "actAs" Permission (a.k.a. Associate SA)

Naming confusion: Google calls it "impersonation" -- it's really "associating a SA with a resource"

# Error without association:
PERMISSION_DENIED: Caller does not have
permission to act as service account
'downloader@project.iam...'

# Fix:
gcloud iam service-accounts \
  add-iam-policy-binding "$TARGET_SA" \
  --member="serviceAccount:$DEPLOYER" \
  --role="roles/iam.serviceAccountUser"

Why the name is confusing

  • Google calls it "impersonation" -- you're associating
  • "serviceAccountUser" = associate SA with a resource
  • Docs page titled: "Attach service accounts to resources"

Where it bites you

  • Creating SA: iam.serviceAccountAdmin
  • Associating SA: iam.serviceAccountUser
  • Creating != associating -- different permission!
KEY SLIDE. actAs sounds like impersonation but it's really "assign this SA to a resource." The role name "serviceAccountUser" is also misleading. Creating an SA requires iam.serviceAccountAdmin, but attaching it requires iam.serviceAccountUser. These are different permissions, different roles. Easy to miss.

Associate in Practice: Who Deploys?

Two valid approaches. We chose Approach A. Audit logs prove only actAs is checked.

Approach A: Terraform Deploys What we use

  • Cloud Build: build + push image ONLY
  • Terraform: creates Cloud Run with runtime SA
  • Associate needed: Deployer SA only

Approach B: Cloud Build Deploys Alternative

  • Cloud Build: build + push + gcloud run deploy
  • Associate needed: Cloud Build SA + deployer on CB SA
  • Faster CI/CD, but broader permissions

tokenCreator: The Authentication Chain

When Cloud Scheduler calls Cloud Run with OIDC auth, someone needs to mint the token

sequenceDiagram
  participant CS as Cloud Scheduler
  participant CSA as Scheduler Agent
  participant SA as Scheduler SA
  participant CR as Cloud Run Job
  CS->>CSA: "I need to call Cloud Run"
  CSA->>CSA: Check: do I have tokenCreator on Scheduler SA?
  CSA->>SA: Generate OIDC token
  SA-->>CS: OIDC token
  CS->>CR: HTTP request + OIDC token
  CR->>CR: Validate token, check run.invoker
  CR-->>CS: 200 OK
  
# Terraform fix (service_accounts.tf):
resource "google_service_account_iam_member" "scheduler_token_creator" {
  service_account_id = google_service_account.scheduler.name
  role               = "roles/iam.serviceAccountTokenCreator"
  member             = "serviceAccount:service-PROJECT_NUM@gcp-sa-cloudscheduler.iam..."
}

If you miss any link: the trigger fires, but authentication fails silently

tokenCreator is the second hidden IAM pattern. The Agent needs tokenCreator permission ON the SA it's minting tokens for. Same pattern for Eventarc: Pub/Sub agent needs tokenCreator on invoker SA. Key distinction: actAs = "associate SA with resource", tokenCreator = "mint auth tokens as SA"

Service Agents Are NOT Auto-Created

Surprise: Enabling an API does not guarantee the service agent SA exists

# You'd expect this to work:
resource "google_project_service" "eventarc" {
  service = "eventarc.googleapis.com"
}
resource "google_project_iam_member" "..." {
  member = "serviceAccount:
    service-NUM@gcp-sa-eventarc..."
  depends_on = [...eventarc]
}
# FAILS: SA does not exist!
# Fix: Explicitly activate agents
resource "null_resource" "init_agents" {
  depends_on = [google_project_service.eventarc]
  provisioner "local-exec" {
    command = <<-SCRIPT
      gcloud beta services identity create \
        --service=storage.googleapis.com
      gcloud beta services identity create \
        --service=eventarc.googleapis.com
    SCRIPT
  }
}

Note: depends_on waits for API "enabled" -- NOT for the service agent to exist

Service agents are lazily created -- first use or explicit identity create. Terraform's depends_on only waits for the API resource to report "created." Common agents: Cloud Storage, Eventarc, Pub/Sub, Cloud Scheduler, Data Fusion.

IAM Propagation: Eventually Consistent

IAM says "granted" but the permission isn't enforced yet (~60s typical, up to 7 min)

Naive: sleep 60

provisioner "local-exec" {
  command = "sleep 60"
}

Wasteful (usually 10-20s). Unreliable (sometimes 7 min). No verification.

Better: Poll testIamPermissions

for i in $(seq 1 12); do
  TOKEN=$(gcloud auth print-access-token \
    --impersonate-service-account="$SA")
  RESP=$(curl -s -H "Auth: Bearer $TOKEN" \
    ".../testPermissions?
     permissions=storage.objects.get")
  if echo "$RESP" | grep -q "objects.get"
  then
    echo "Confirmed after $((i*10))s"
    exit 0
  fi
  sleep 10
done

This pattern caught a real bug: Cloud Build SA had roles granted but couldn't access the build bucket for 45 seconds after terraform apply.

Terraform grants IAM role -> API returns success -> next resource tries permission -> fails. Intermittent: sometimes 5s, sometimes 60s, sometimes 7 minutes. The testIamPermissions polling approach makes terraform apply deterministic. Policy Troubleshooter API (gcloud policy-troubleshoot iam) is another option for debugging.

The Eventarc Chain: 5 Bindings, All Required

Miss one binding and it fails silently

flowchart LR
  GCS[GCS\nfile upload] -->|"1. Storage agent\npubsub.publisher"| PS[Pub/Sub]
  PS -->|"2. Eventarc agent\neventReceiver"| EA[Eventarc]
  EA -->|"3. Invoker SA\nrun.invoker ON service"| CR[Cloud Run\nService]
  EA -.->|"4. Invoker SA\neventarc.eventReceiver"| EA
  PS -.->|"5. Pub/Sub agent\ntokenCreator ON invoker SA"| INV[Invoker SA]
  INV -->|OIDC token| CR
  style GCS fill:#e6f4ea,stroke:#188038
  style CR fill:#e8eaf0,stroke:#1a56db
  
# Trigger depends_on ALL 5 bindings -- miss one = silent failure
resource "google_eventarc_trigger" "main" {
  depends_on = [
    ...storage_pubsub_publisher,     # 1
    ...eventarc_event_receiver,      # 2
    ...invoker_processor,            # 3
    ...invoker_event_receiver,       # 4
    ...pubsub_token_creator,         # 5
  ]
}
Hardest bug: trigger fires, event is delivered, Cloud Run returns 403. No error in Eventarc logs. Had to trace: Pub/Sub -> OIDC token -> invoker SA -> run.invoker. 5 bindings, all required, failure is silent.

Key Takeaways

  1. Least privilege needs 3 layers -- Deployer, Runtime SAs, Service Agents
  2. actAs (associate) and tokenCreator are hidden requirements -- missing one = silent failure
  3. Service agents are lazy -- gcloud beta services identity create before granting IAM
  4. IAM is eventually consistent -- poll testIamPermissions, don't sleep
  5. IaC proves itself on destroy + reprovision -- can't rebuild? not automated
