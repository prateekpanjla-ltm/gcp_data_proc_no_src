Why Terraform?

  • Every resource and permission is a line of code in Git
  • One command deploys, one command destroys

IAM Issues Discovered While Using Terraform

  • actAs (associate) — deployer needs permission to assign SAs to resources
  • tokenCreator — service agents need permission to mint auth tokens
  • Service agents not auto-created — must be explicitly activated
  • IAM propagation delay — permissions granted but not yet enforced (up to 7 min)
  • Orphaned IAM bindings — deleted SAs leave broken references in IAM policy
  • Silent failures — Eventarc chain: 5 bindings, miss one = no error in logs

The "actAs" Permission (a.k.a. Associate SA)

Naming confusion: Google calls it "impersonation" — it's also "associating a SA with a resource"

# Error without association:
PERMISSION_DENIED: Caller does not have
permission to act as service account
'downloader@project.iam...'

# Fix:
gcloud iam service-accounts \
  add-iam-policy-binding "$TARGET_SA" \
  --member="serviceAccount:$DEPLOYER" \
  --role="roles/iam.serviceAccountUser"

Why the name is confusing

  • Google calls it "impersonation" — you're associating
  • "serviceAccountUser" = associate SA with a resource
  • Docs page titled: "Attach service accounts to resources"
  • Creating SA needs iam.serviceAccountAdmin
  • Associating SA needs iam.serviceAccountUser
  • Creating != associating — different permission!

  TF[Terraform Deployer SA] -->|"1. CREATE SA\niam.serviceAccountAdmin"| SA[Processor SA\nnewly created]
  TF -->|"2. ASSOCIATE SA\niam.serviceAccountUser\n(actAs)"| CR[Cloud Run Service\nservice_account = processor-sa]
  SA -.->|"attached to"| CR
  TF -.->|"Without actAs:\nCREATE succeeds\nASSOCIATE fails ❌"| CR

Associate in Practice: Who Deploys?

Two valid approaches. We chose Approach A. Audit logs prove only actAs is checked.

Approach A: Terraform Deploys What we use

  • Cloud Build: build + push image ONLY
  • Terraform: creates Cloud Run with runtime SA
  • Associate needed: Deployer SA only
  • Deployer needs actAs on Cloud Build SA (to submit build)
  • Deployer needs actAs on runtime SAs (to attach to Cloud Run)

tokenCreator: The Authentication Chain

This involves Google-managed Service Agents (not our Service Accounts). Service agents handle infrastructure plumbing — routing events, minting tokens — and need explicit permission grants.

The Problem

  • Cloud Scheduler needs to call Cloud Run via HTTP
  • Cloud Run requires authentication (OIDC token)
  • Scheduler can't mint tokens — it delegates to its service agent
  • The Scheduler service agent (Google-managed) needs tokenCreator ON the scheduler SA to mint the token

Same pattern for Eventarc (Pub/Sub service agent)

  • GCS event → Pub/Sub service agent delivers to Cloud Run
  • Pub/Sub agent needs tokenCreator ON invoker SA
  • Without it: event delivered, Cloud Run returns 403 silently
# Terraform: grant tokenCreator to SERVICE AGENT
resource "google_service_account_iam_member" "token" {
  service_account_id = google_service_account.scheduler.name
  role         = "roles/iam.serviceAccountTokenCreator"
  # member is the SERVICE AGENT, not our SA:
  member       = "serviceAccount:service-NUM@gcp-sa-cloudscheduler..."
}
sequenceDiagram
  participant CS as Cloud Scheduler
  participant CSA as Scheduler Service Agent
  participant SA as Scheduler SA
  participant CR as Cloud Run Job
  CS->>CSA: I need to call Cloud Run
  CSA->>CSA: Do I have tokenCreator?
  CSA->>SA: Generate OIDC token
  SA-->>CS: OIDC token
  CS->>CR: HTTP + OIDC token
  CR->>CR: Validate token
  CR-->>CS: 200 OK

Key: actAs = associate SA with resource (deploy time) | tokenCreator = service agent mints auth tokens (runtime)

Service Agents Are NOT Auto-Created

Surprise: Enabling an API does not guarantee the service agent SA exists

# You'd expect this to work:
resource "google_project_service" "eventarc" {
  service = "eventarc.googleapis.com"
}
resource "google_project_iam_member" "..." {
  member = "serviceAccount:
    service-NUM@gcp-sa-eventarc..."
  depends_on = [...eventarc]
}
# FAILS: SA does not exist!
# Fix: Explicitly activate agents
resource "null_resource" "init_agents" {
  depends_on = [google_project_service.eventarc]
  provisioner "local-exec" {
    command = <<-SCRIPT
      gcloud beta services identity create \
        --service=storage.googleapis.com
      gcloud beta services identity create \
        --service=eventarc.googleapis.com
    SCRIPT
  }
}

In Terraform, we use a null_resource with local-exec to run gcloud beta services identity create for each service. IAM grants then use Terraform's depends_on (which controls resource creation order) to wait for this activation step before attempting to grant permissions to the agent.

Note: Terraform's depends_on only ensures ordering — it waits for the API resource to report "enabled", NOT for the service agent to actually exist. That's why the explicit activation step is needed.

IAM Propagation: Eventually Consistent

IAM says "granted" but the permission isn't enforced yet (~60s typical, up to 7 min)

Naive: sleep 60

provisioner "local-exec" {
  command = "sleep 60"
}

Wasteful (usually 10-20s). Unreliable (sometimes 7 min). No verification.

Better: Poll + Policy Troubleshooter

for i in $(seq 1 18); do
  # Check 1: tokenCreator propagated?
  # Check 2: cloudbuild.builds.create?
  # Check 3: storage.objects.create?
  # Check 4: storage.objects.get?
  gcloud policy-troubleshoot iam \
    "//cloudresourcemanager.../projects/$P"\
    --principal-email="$SA" \
    --permission="cloudbuild.builds.create"
  # If all GRANTED -> proceed
  sleep 10
done
sequenceDiagram
  participant TF as Terraform
  participant IAM as GCP IAM
  participant PT as Policy Troubleshooter
  participant CB as Cloud Build
  TF->>IAM: Grant roles to Cloud Build SA
  IAM-->>TF: OK (recorded, not yet enforced)
  loop Every 10s, up to 180s
    TF->>PT: Check 1: tokenCreator propagated?
    TF->>PT: Check 2: cloudbuild.builds.create?
    TF->>PT: Check 3: storage.objects.create?
    TF->>PT: Check 4: storage.objects.get?
    PT-->>TF: NOT YET / GRANTED
  end
  TF->>CB: gcloud builds submit (all 4 GRANTED)

The Eventarc Chain: 5 Bindings, All Required

Miss one binding and it fails silently. This chain is used in Phase 2 (GCS → processor) and Phase 3 (GCS → BQ loader). Three service agents involved: Storage, Eventarc, and Pub/Sub.

flowchart LR
  GCS[GCS\nfile upload] -->|"1. Storage agent\npubsub.publisher"| PS[Pub/Sub]
  PS -->|"2. Eventarc agent\neventReceiver"| EA[Eventarc]
  EA -->|"3. Invoker SA\nrun.invoker ON service"| CR[Cloud Run\nService]
  EA -.->|"4. Invoker SA\neventarc.eventReceiver"| EA
  PS -.->|"5. Pub/Sub agent\ntokenCreator ON invoker SA"| INV[Invoker SA]
  INV -->|OIDC token| CR
  style GCS fill:#e6f4ea,stroke:#188038
  style CR fill:#e8eaf0,stroke:#1a56db

What "silent failure" means

  • File uploads to GCS — succeeds
  • Event fires via Eventarc — succeeds
  • Event reaches Cloud Run — succeeds
  • But auth fails (missing binding #5) — no error in Eventarc logs
  • Only visible in Cloud Run logs as 403

Service agents in this chain

  • service-NUM@gs-project-accounts — Storage agent (#1)
  • service-NUM@gcp-sa-eventarc — Eventarc agent (#2)
  • service-NUM@gcp-sa-pubsub — Pub/Sub agent (#5)
  • All must be activated + granted permissions explicitly

Orphaned IAM Bindings After Destroy

When Terraform destroys SAs, GCP renames them to deleted:serviceAccount:email?uid=... but IAM bindings referencing them remain in the project policy.

The problem

  • After terraform destroy, deleted SAs leave orphaned references
  • On redeploy, Terraform creates SA with same email but new UID
  • Old orphaned bindings can conflict with new ones
  • We found 20+ orphaned entries in our project after destroy
# Check for orphaned bindings:
gcloud projects get-iam-policy PROJECT \
  --format=json | grep "deleted:serviceAccount:"

# Example output:
"deleted:serviceAccount:test-cloud-build@
  project.iam...?uid=113536875676481232802"

The fix (automated in destroy script)

  • Added as final step in destroy-all-phases.sh
  • Fetches project IAM policy as JSON
  • Strips all deleted:serviceAccount:... members
  • Re-applies cleaned policy
  • Runs automatically on every destroy
flowchart LR
  D[terraform destroy] --> O[Orphaned bindings\ndeleted:serviceAccount:...]
  O --> C[Cleanup script\nstrips deleted members]
  C --> P[Clean IAM policy\nready for redeploy]

  style P fill:#e6f4ea,stroke:#188038

Key Takeaways

  1. Least privilege needs 3 stages — Deployer, Runtime SAs, Service Agents
  2. actAs (associate) and tokenCreator are hidden requirements — missing one = silent failure
  3. Service agents are lazy — gcloud beta services identity create before granting IAM
  4. IAM is eventually consistent — poll with Policy Troubleshooter, don't sleep
  5. IaC proves itself on destroy + reprovision — can't rebuild? not automated
